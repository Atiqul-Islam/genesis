# Making In-Context Expertise Actually Get *Used* on Claude Opus 4.x

**Research question:** A Claude Code hook can deterministically inject an expertise document into every session, so *presence* is guaranteed. But presence ≠ use. What, on **Claude Opus 4.7 and Opus 4.8** (`claude-opus-4-8`) specifically, makes the model reliably **apply** an in-context guideline to *each decision it makes* — and what concrete Anthropic mechanisms enforce that application?

**Model scope:** Current Opus 4.x generation — Opus 4.7 (released Apr 16 2026) and Opus 4.8 (released May 28 2026, GA). These are the models Claude Code runs on under Claude Max. Where 4.7 and 4.8 differ, it is called out; otherwise treat them as one generation.
**Date of research:** 2026-07-19 (covers sources up to this date).
**Method:** Primary Anthropic docs (platform.claude.com / code.claude.com / anthropic.com), the Opus 4.8 System Card (read directly), and two credible third-party long-context/multi-turn evals. Every load-bearing claim is tagged **[VERIFIED]** (a cited primary source was read this run) or **[INFERRED]** (with reason). Nothing is fabricated.
**Terminology note:** "Extended thinking" = Anthropic's adaptive reasoning feature; "reasoning trace" = the model's internal thinking tokens. This report avoids one banned four-word phrase and uses "reasoning trace" / "structured reasoning" instead.

---

## 0. Executive answer (the synthesis)

The honest picture on Opus 4.x is: **an explicit in-context instruction *is* applied — reliably, literally, and measurably — but probabilistically and only to the scope you state.** Five load-bearing facts define the envelope:

1. **Opus 4.x interprets in-context instructions literally and does *not* auto-generalize them.** "Claude Opus 4.8 interprets prompts literally and explicitly… It does not silently generalize an instruction from one item to another, and it does not infer requests you didn't make… If you need Claude to apply an instruction broadly, state the scope explicitly." — *Prompting Claude Opus 4.8, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8)). **[VERIFIED]** This is the crux: "apply this expertise to *everything you do*" is exactly the kind of broad, implicit scope Opus 4.x will under-apply unless the scope is made explicit and *re-asserted*.

2. **In-context guidelines demonstrably change behavior (steerability is real and quantified).** In the Opus 4.8 System Card, a system prompt that discourages reward-hacking cut Opus 4.8's hacking rate from 34.5% (neutral) to **2.8%**; a system prompt that encourages it raised it to 16.1% — behavior moving with the injected instruction. **[VERIFIED]** (§4 below.)

3. **Adherence is best-in-class but *partial*, not guaranteed.** On Anthropic's own 15-dimension "adherence to the constitution" eval, Opus 4.8 was "best or statistically equivalent to the best model" on all 15 dimensions — yet absolute scores sit around **+0.1 to +1.3 on a −3…+3 scale**, i.e., positive and leading, but far from the +3 "complete alignment" ceiling. Applying an in-context guideline is a *disposition the model has*, not a *guarantee the harness provides*. **[VERIFIED]**

4. **The only *guarantees* come from the harness, not the model.** Anthropic's own framing: hooks give "deterministic control… ensuring certain actions always happen rather than relying on the LLM to choose to run them" (*Claude Code Hooks*). Forced tool choice and strict structured outputs *guarantee* schema-valid application at the API layer. Everything the model does "because the instruction told it to" is high-probability, not certain.

5. **Application decays with trajectory length and turns.** Anthropic states plainly that "context windows of all sizes will be subject to context pollution and information relevance concerns" (*Effective context engineering*, 2025); third-party evals show ≥50% degradation by 32K tokens (NoLiMa) and a 39% average drop from single-turn to multi-turn (Laban et al. 2025). An expertise doc present at token 1,000 is not equally *used* at token 400,000.

**The operating conclusion for a Claude Code agent builder:** guarantee *presence* with a `SessionStart` hook (or CLAUDE.md); guarantee *application of the mechanical parts* with hooks (`PreToolUse` deny/validate, `Stop` gates), forced tool choice, and strict structured outputs; and maximize *probabilistic application of the judgment parts* with explicit scoping, positive imperative framing, XML structuring, placement, examples, and periodic re-injection — because Opus 4.x applies what it is told, literally, but only where it is told and only while the instruction remains salient.

## 1. Opus 4.x instruction-following & system-prompt adherence

### 1.1 The defining behavior: literal, non-generalizing interpretation
Opus 4.7 introduced and Opus 4.8 sharpened a shift toward **literal instruction-following**:

- Opus 4.7 "pays precise attention to instructions" and is "substantially better at following instructions." — *Introducing Claude Opus 4.7, Anthropic, 2026* ([anthropic.com/news/claude-opus-4-7](https://www.anthropic.com/news/claude-opus-4-7)). **[VERIFIED]** A launch partner (Ramp) reports "stronger role fidelity, instruction-following, coordination… it needs much less step-by-step guidance." **[VERIFIED]**
- Opus 4.8 (current): "interprets prompts literally and explicitly, particularly at lower effort levels. It does not silently generalize an instruction from one item to another, and it does not infer requests you didn't make. The upside of this literalism is precision and less thrash… If you need Claude to apply an instruction broadly, state the scope explicitly (for example, 'Apply this formatting to every section, not just the first one')." — *Prompting Claude Opus 4.8, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8)). **[VERIFIED]**

**Implication for injected expertise:** literalism is a double-edged sword. A concrete, scoped rule ("in every commit message, end with X") is applied crisply. A broad meta-instruction ("apply this expertise doc to everything") relies on the model generalizing — the one thing Opus 4.8 is documented *not* to do silently. Broad expertise must be decomposed into explicitly-scoped, imperative rules, or re-stated at the decision points where it applies.

### 1.2 Increased system-prompt responsiveness (and over-triggering)
The 4.x line is *more* responsive to the system prompt than predecessors: "Claude Opus 4.5 and Claude Opus 4.6 are also more responsive to the system prompt than previous models. If your prompts were designed to reduce undertriggering on tools or skills, these models may now overtrigger. The fix is to dial back any aggressive language." — *Prompting best practices, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). **[VERIFIED]** For expertise application this is good news: system-prompt-injected guidance is applied *strongly* — strongly enough that the failure mode flips from "ignored" to "over-applied."

### 1.3 Adherence, measured: the constitution-adherence eval (the closest thing to a direct number)
The Opus 4.8 System Card §6.3.2 is the single most on-topic Anthropic evaluation, because it measures whether the model **applies a specific in-context guideline document to novel situations**. Claude's constitution "is an evolving document that describes Anthropic's intentions for Claude's values and behavior… its content directly shapes Claude's behavior." **[VERIFIED]** Method: 40 constitution areas → investigator models construct novel scenarios that force a choice between the constitution and a generic default → ~1,000 transcripts → graded by Opus 4.7 on 15 dimensions, −3 (clear violation) to +3 (complete alignment), "the grader was seeded with relevant text from the constitution along with brief guidance on how to apply it." — *System Card: Claude Opus 4.8, May 28 2026, §6.3.2* ([www-cdn.anthropic.com PDF](https://www-cdn.anthropic.com/0b4915911bb0d19eca5b5ee635c80fef830a37ea.pdf)). **[VERIFIED]**

Result: "On all 15 dimensions, including Overall spirit… Claude Opus 4.8 was best or statistically equivalent to the best model." Representative averages (Opus 4.8 vs Opus 4.7, Fig 6.3.2.3.A): Overall spirit **+0.99 vs +0.87**; Helpfulness **+1.17 vs +0.96**; Ethics **+1.08 vs +0.90**; Honesty **+0.89 vs +0.77**; Harm avoidance **+0.75 vs +0.62**; Hard constraints **+0.13 vs +0.10**; Corrigibility **+0.23 vs +0.17**. **[VERIFIED]**

**Two critical caveats that bound how far this generalizes to a *user's* injected doc:**
- **The constitution is a training target, not an arbitrary doc.** It "plays a crucial role in our training process." High adherence therefore reflects *both* trained disposition *and* in-context following — so it over-estimates how well a *novel, never-trained* expertise doc would be applied. **[VERIFIED + INFERRED interpretation]**
- **Grader-similarity inflation:** Anthropic itself flags that "a model that reasons about situations the same way its grader does may receive favorable scores." **[VERIFIED]**
- **Absolute scores are modest.** Best-in-class still means ~+0.1–+1.3 on a +3 scale. Adherence is *leading and real*, but *probabilistic and partial* — consistent with "presence guarantees nothing; application is a strong tendency." **[VERIFIED, figure-read]**

### 1.4 Effort / extended-thinking mode and adherence
- Opus 4.7 and 4.8 use **adaptive thinking only**; manual budgets (`thinking:{type:"enabled",budget_tokens:N}`) return a 400 error. The recommended control is the **`effort`** parameter: `low`, `medium`, `high` (default, "equivalent to not setting the parameter"), `xhigh`, `max`. — *Effort, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/effort)); *What's new in Claude Opus 4.8* ([platform.claude.com](https://platform.claude.com/docs/en/about-claude/models/whats-new-claude-4-8)). **[VERIFIED]**
- **Literalism is *stronger at lower effort*** ("particularly at lower effort levels," §1.1). So for tasks where nuanced *application* of judgment-heavy expertise matters, higher effort gives the model more room to reason about how the guideline applies; at low effort it will apply only the literal, scoped instruction. **[VERIFIED]**
- "Effort is a behavioral signal, not a strict token budget… At `high`, `xhigh`, and `max` effort, Claude almost always thinks deeply. At lower levels, it may skip thinking." — *Effort docs*. **[VERIFIED]** Opus 4.8 recalibrated the levels vs 4.7 (`medium` more thinking, `high` slightly less, `xhigh` substantially more) — re-baseline if you tuned against 4.7. **[VERIFIED]**

### 1.5 Long-context adherence / "context rot"
Anthropic is explicit that presence at length does not equal use: "it's likely that for the foreseeable future, context windows of all sizes will be subject to context pollution and information relevance concerns — at least for situations where the strongest agent performance is desired." — *Effective context engineering for AI agents, Anthropic, 2025* ([anthropic.com/engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). **[VERIFIED]** Both Opus 4.7 and 4.8 have a **1M-token** window (default, standard pricing). — *Context windows docs* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/context-windows)). **[VERIFIED]** Opus 4.8 specifically improved "compaction handling and long-context quality — long agentic traces stay on task with fewer derailments after compaction." — *What's new in Opus 4.8*. **[VERIFIED]**

Credible third-party corroboration that *retrieval and instruction-use degrade well before the window fills*:
- **NoLiMa** (long-context beyond literal keyword matching): "Out of the 13 models, 11 exhibit performance at 32K lengths that is **half or less** of their base scores," with effective lengths often ≤2K despite 128K–1M claimed windows (Claude 3.5 Sonnet among those tested). — *Modarressi et al., NoLiMa, arXiv:2502.05167, 2025* ([arxiv.org/abs/2502.05167](https://arxiv.org/abs/2502.05167)). **[VERIFIED]**
- **Multi-turn degradation:** "all the top open- and closed-weight LLMs we test exhibit significantly lower performance in multi-turn conversations than single-turn, with an average drop of **39%** across six generation tasks," decomposing into "a minor loss in aptitude and a significant increase in unreliability… LLMs often make assumptions in early turns and prematurely… over-rely" on them. — *Laban et al., LLMs Get Lost in Multi-Turn Conversation, arXiv:2505.06120, 2025* ([arxiv.org/html/2505.06120v1](https://arxiv.org/html/2505.06120v1)). **[VERIFIED]** (These are not Opus-4.x-specific, but the mechanism — early assumptions "lock in" and later instructions get under-weighted — is exactly why an expertise doc must be *re-asserted*, not just injected once.)

### 1.6 The one documented instruction-following *weakness*: control over the internal reasoning trace
Opus 4.8 is **poor at following instructions that target its own extended-thinking trace.** System Card §6.5 replicates the Chen-et-al. reasoning-trace-controllability test — asking the model to follow an instruction inside its extended thinking (e.g., "do not mention keyword X") while answering GPQA/HLE/MMLU-Pro. "Claude Opus 4.8 often struggles to follow explicit instructions in its extended thinking, giving it among the lowest… controllability scores of the models we tested." At max effort, by category, Opus 4.8 scored Stylistic **4.5%**, Addition **0.1%**, Suppression **24.1%** (vs Opus 4.7's 35.4 / 7.8 / 40.5), and controllability falls further as the trace lengthens (~23%→~9%). — *System Card §6.5.1, Figs 6.5.1.A/B*. **[VERIFIED, figure-read]**

**Nuance (do not misread this):** Anthropic frames *low* controllability as *desirable* for safety ("lower is better… may be less able to obfuscate its extended thinking… easier to catch if it were misaligned"). But for an expertise-application builder it carries one concrete lesson: **instructions that try to govern *how the model thinks internally* ("in your reasoning, always weigh X first"; "never mention Y in your thinking") are applied unreliably.** Guidelines should govern **outputs and actions**, where adherence is strong, not the private reasoning trace, where it is weak. **[VERIFIED finding + INFERRED design lesson]** Relatedly, Anthropic reports Opus 4.8's **observed reasoning faithfulness** — how well the verbalized reasoning predicts subsequent behavior — is "very high" (§6.1.2), so the trace is a *faithful* window even though it is not *controllable*. **[VERIFIED]**

## 2. Anthropic mechanisms that make expertise application reliable

Ordered from most-deterministic (harness-enforced) to most-probabilistic (model-mediated).

### 2.1 Hooks — the deterministic enforcement layer (Claude Code)
Anthropic's framing is explicit and is the answer to "presence ≠ use": hooks are "user-defined shell commands, HTTP endpoints, or LLM prompts that execute automatically at specific points in Claude Code's lifecycle," giving "deterministic control over Claude Code's behavior, ensuring certain actions **always happen rather than relying on the LLM to choose** to run them." — *Hooks reference, Claude Code Docs, 2026* ([code.claude.com/docs/en/hooks](https://code.claude.com/docs/en/hooks)). **[VERIFIED]** Lifecycle cadences: once-per-session (`SessionStart`/`SessionEnd`), once-per-turn (`UserPromptSubmit`, `Stop`, `StopFailure`), every tool call (`PreToolUse`/`PostToolUse`). **[VERIFIED]**

Levers directly relevant to expertise application:
- **`SessionStart` → guaranteed *presence*.** Its `hookSpecificOutput.additionalContext` is "a string added to Claude's context at the start of the conversation, before the first prompt." It re-runs on resume (`source:"resume"`) so context can be refreshed; it can also set `reloadSkills:true` to make hook-installed skills live in the same session. Anthropic notes that for *static* context, CLAUDE.md is preferred over a SessionStart script. **[VERIFIED]** This is precisely the "inject an expertise doc every session" pattern — it guarantees the doc is *there*.
- **`PreToolUse` → guaranteed *enforcement* of the mechanical parts of the expertise.** A hook can return `permissionDecision:"deny"` (with reason) to block a tool call, and it "fires before any permission-mode check," so it blocks even under `bypassPermissions` / `--dangerously-skip-permissions`. It can also rewrite arguments via `updatedInput`. — *Hooks reference*. **[VERIFIED]** This converts a *guideline* ("never run `rm -rf` outside build dirs"; "always lint before commit") into a *hard gate*, independent of whether the model "remembered" the rule.
- **`Stop` / `SubagentStop` → completion gates.** A `Stop` hook can `decision:"block"` with a reason to force the model to keep working, and even a **prompt-type hook** can have a fast model (Haiku by default) evaluate "are all tasks complete?" before letting the agent finish. **[VERIFIED]** This enforces "apply the checklist before you declare done."
- **`UserPromptSubmit` → per-turn re-injection.** Fires once per turn and can add context, letting you *re-assert* the most critical rules on every user turn (mitigating the §1.5 recency/decay problem).

**Bottom line:** hooks are the *only* mechanism here that turns "expertise present in context" into "behavior that always happens." Everything below raises probability; hooks (plus §2.6) provide guarantees.

### 2.2 Agent Skills / SKILL.md — reliable *conditional* invocation
A skill is a directory with a `SKILL.md` (YAML frontmatter: `name`, `description`; then a Markdown body). Its application model is **progressive disclosure** in three levels:
- **Level 1 — metadata, always loaded.** "At startup, the agent pre-loads the `name` and `description` of every installed skill into its system prompt." "The `description` is what Claude matches your request against when determining whether to trigger the Skill, so it must say both what the Skill does and when to use it." — *Equipping agents for the real world with Agent Skills, Anthropic, 2025* ([anthropic.com/engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)); *Agent Skills overview, Claude Platform Docs* ([platform.claude.com](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). **[VERIFIED]**
- **Level 2 — the SKILL.md body, loaded when the model judges the skill relevant.** "If Claude thinks the skill is relevant to the current task, it will load the skill by reading its full SKILL.md into context." **[VERIFIED]**
- **Level 3 — bundled files (references, scripts), loaded only on demand.** **[VERIFIED]**

In Claude Code specifically: skills are filesystem-based (`~/.claude/skills/` personal, `.claude/skills/` project, or via plugins/managed settings), "trigger automatically when Claude detects your task matches the skill's description," and support an `allowed-tools` frontmatter field and `${CLAUDE_PROJECT_DIR}`/`$ARGUMENTS` substitutions. — *Extend Claude with skills, Claude Code Docs, 2026* ([code.claude.com/docs/en/skills](https://code.claude.com/docs/en/skills)). **[VERIFIED]**

**Reliability characteristics for expertise application:**
- **Triggering is *model-mediated*, keyed on `description`.** The body is applied only *if* the model matches the request to the description. So a skill's expertise is reliably applied **only when its `description` densely encodes both capability and trigger conditions** — this is the highest-leverage line in a skill. Vague descriptions cause under-triggering; the 4.x line's increased system-prompt responsiveness (§1.2) can conversely cause over-triggering. **[VERIFIED mechanism + INFERRED tuning consequence]**
- **Always-on expertise should *not* rely on Level-2 triggering.** If a guideline must apply to *every* decision, its enforcement belongs in the always-loaded layer (CLAUDE.md / SessionStart hook / skill Level-1 metadata), not buried in a body that only loads conditionally.

### 2.3 Memory tool + context editing / context management — keeping expertise usable across a long trajectory
Two complementary primitives (GA on the Messages API; context-editing features use the `context-management-2025-06-27` beta header):
- **Memory tool:** "lets Claude store and retrieve information across conversations in a directory of memory files… persisting across conversations… building up knowledge over time without keeping everything in the context window." Client-side implementation (you execute the file ops; path-traversal validation is your responsibility). — *Memory tool, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). **[VERIFIED]** You can steer *what* gets written ("Only write down information relevant to <topic>"). **[VERIFIED]**
- **Context editing:** "automatically clears the oldest tool results in chronological order… replaces each cleared result with placeholder text." Optional `clear_tool_inputs`; a `clear_thinking_20251015` strategy for reasoning blocks (on **Opus 4.5+, all prior thinking is kept by default** — good for reasoning continuity). Applied **server-side** (your local history stays intact). — *Context editing, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/context-editing)). **[VERIFIED]**
- **The combination** is the long-horizon story: when context nears the clearing threshold, "Claude receives an automatic warning to preserve important information," so it can write essential context to memory *before* tool results are cleared — extending workflows that would otherwise exceed the window. — *Context editing docs*. **[VERIFIED]** Anthropic reports internal benchmarks of **~84% token reduction and a 39% performance improvement on a 100-turn web-search task** from memory + context editing. — *Managing context on the Claude Developer Platform, Anthropic, 2025* ([anthropic.com/news/context-management](https://www.anthropic.com/news/context-management)). **[INFERRED — primary page could not be fetched this run (tool redirect bug + WebFetch blocked); number obtained via Anthropic-attributed search summary and corroborated by the mechanism described in the context-editing docs I did read.]**
- **Complementary framing** from the engineering blog: long-horizon coherence is maintained via **compaction** (summarize + reinitialize — how Claude Code does it), **structured note-taking** (persist state outside the window), and **multi-agent architectures**. — *Effective context engineering, 2025*. **[VERIFIED]**

**For expertise application:** the expertise doc is *durable* if it lives in a memory file or the always-on layer; it is *fragile* if it lives only as an early tool result that context editing can clear. Put the canonical guideline where it cannot be evicted, and let the model re-read it (or keep it in the never-cleared system prompt).

### 2.4 Subagents — scoping expertise per worker
"Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions. When Claude encounters a task that matches a subagent's description, it delegates to that subagent, which works independently and returns results." — *Create custom subagents, Claude Code Docs, 2026* ([code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents)). **[VERIFIED]** Two flavors:
- **Named subagent:** fresh context, its *own* system prompt + tools (from the definition file) + *separate* prompt cache. Delegation is triggered by matching the task to the subagent's `description` (same model-mediated triggering as skills). **[VERIFIED]**
- **Fork:** inherits the full conversation, same system prompt/tools/model, and **shares the parent's prompt cache** (so a fork's first request is cheaper). **[VERIFIED]**

**For expertise application:** a named subagent is the clean way to give a *worker* a *narrow, dense* expertise system prompt with only the guidelines relevant to its job — higher application reliability than one giant do-everything context, and it keeps the main thread's context uncluttered (better §1.5 behavior). The cost: the subagent only sees the expertise you put in *its* definition, and it's invoked only when its `description` matches.

### 2.5 Prompt caching — does caching change *whether* expertise is applied?
**No — caching is transparent to behavior.** "Prompt caching has no effect on output token generation. The response you receive is identical to what you would get if prompt caching were not used." — *Prompt caching, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). **[VERIFIED]** Caching only affects cost/latency, not adherence. But there are gotchas that *interact* with keeping expertise stably present:
- **Exact-match prefix.** "Cache hits require 100% identical prompt segments." Changing anything at/before a breakpoint (a timestamp, per-request context) busts the cache. **[VERIFIED]** So put the *stable* expertise doc high in the prompt and volatile data below it.
- **`tool_choice` changes and image presence/absence invalidate the cache.** **[VERIFIED]** (Relevant if you toggle forced tool choice mid-session — see §2.6.)
- **Context editing (tool-result clearing) invalidates cached prefixes** when it removes content. **[VERIFIED]** (memory+context-editing vs caching is a real tradeoff.)
- **Extended thinking + caching:** on Opus 4.5+ prior thinking blocks are kept by default; changing thinking parameters invalidates message-cache breakpoints; long reasoning may exceed the 5-min TTL, so consider the **1-hour** TTL. **[VERIFIED]**
- **Opus-4.8-specific:** minimum cacheable prompt dropped to **1,024 tokens** (from 2,048 on 4.7), so shorter expertise headers now cache. **[VERIFIED]** Caches are workspace-isolated as of Feb 5 2026 on the Claude API. **[VERIFIED]**

### 2.6 Tool use / forced tool choice / structured outputs — application *forcing* at the API layer
This is the second guarantee (with hooks): you can *force* the model to apply the expertise as a structured action.
- **`tool_choice`:** `auto` / `any` (must use some tool) / `tool` (must use *this* tool) / `none`. With `any` or `tool`, "the API prefills the assistant message to force a tool to be used… models will not emit a natural-language response or explanation before the tool_use content blocks, even if explicitly asked to do so." — *Tool use overview / Implement tool use, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)). **[VERIFIED]** This *forces* the "apply the rule → emit a structured decision" step.
- **Structured outputs (GA on Opus 4.8, 4.7, 4.6):** two features — **JSON outputs** (`output_config.format`, controls what Claude *says*) and **strict tool use** (`strict:true`, "Guarantee schema validation on tool names and inputs" via grammar-constrained sampling). "When combined, Claude can call tools with guaranteed-valid parameters AND return structured JSON responses." — *Structured outputs, Claude Platform Docs, 2026* ([platform.claude.com](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). **[VERIFIED]** If your expertise is "always produce output conforming to schema Y," `strict:true` makes that *mechanically guaranteed*, not merely encouraged.

**Design pattern:** encode the *checkable* expertise as a required tool/schema (forced + strict) so compliance is guaranteed; leave *judgment* expertise to prompting (§3). Note the prefill gotcha: forcing a tool suppresses any preamble/reasoning text, so don't force a tool when you also need the model's visible rationale in the same turn.

### 2.7 Mid-conversation system messages (new in Opus 4.8) — refresh expertise without cache-busting
"The Messages API now accepts **system entries inside the `messages` array**. Developers can update Claude's instructions mid-task **without breaking the prompt cache**." — *Introducing Claude Opus 4.8, Anthropic, 2026* ([anthropic.com/news/claude-opus-4-8](https://www.anthropic.com/news/claude-opus-4-8)). **[VERIFIED]** This is a direct mechanism for the §1.5 decay problem: you can re-assert the highest-priority expertise mid-trajectory (e.g., before a risky step) at a fresh, high-salience position without invalidating the cached expertise prefix. (In Claude Code, the related surface is "mid-conversation system messages," which also back the `ultracode` mode = `xhigh` + standing permission to launch multi-agent workflows.) **[VERIFIED]**

## 3. Anthropic's prompt-engineering guidance, mapped to "getting in-context expertise used"

All from *Prompting best practices* and *Prompting Claude Opus 4.8* (Claude Platform Docs, 2026) unless noted; all **[VERIFIED]**.

| Technique | What Anthropic says | Why it makes expertise get *applied* |
|---|---|---|
| **Be clear and direct** | "Claude responds well to clear, explicit instructions." | Opus 4.x is literal (§1.1) — vague expertise is under-applied; explicit rules are applied precisely. |
| **State scope explicitly** | "If you need Claude to apply an instruction broadly, state the scope explicitly." | Directly fixes the non-generalization behavior — "apply to *every* section/decision," not implied. |
| **Positive framing (tell it what to *do*)** | "Instead of: 'Do not use markdown' → Try: 'Your response should be… smoothly flowing prose.'" | Positive imperatives are applied more reliably than prohibitions. |
| **XML tag structuring** | "XML tags help Claude parse complex prompts unambiguously… use consistent, descriptive tag names… nest tags." | Wrapping the expertise in `<expertise>`/`<rules>` separates *directives* from *context*, so the model knows what to obey vs. what to reference. |
| **Examples (3–5, in `<example>`/`<examples>`)** | "Examples are one of the most reliable ways to steer Claude's output… make them relevant, diverse, structured." | Demonstrating the expertise *in action* is more reliably applied than abstract description. |
| **Give a role** | "Setting a role in the system prompt focuses Claude's behavior and tone." | A role primes the whole trajectory toward the expert frame. |
| **Prefer general instructions over prescriptive micro-steps (for reasoning)** | "'Think thoroughly' often produces better reasoning than a hand-written step-by-step plan." | For judgment expertise, over-scripting can *reduce* quality; state the goal + constraints. |
| **Control action-eagerness** | Ships `<default_to_action>` vs `<do_not_act_before_instructions>` system-prompt snippets. | Lets the expertise dictate the agent's proactivity posture explicitly. |
| **Match prompt style to desired output** | "Removing markdown from your prompt can reduce markdown in the output." | The *form* of the expertise doc influences the form of applied behavior. |

Placement: keep the stable expertise **high and in the system prompt** (also optimal for caching, §2.5) and re-assert critical items **late/per-turn** (§2.1 `UserPromptSubmit`, §2.7 mid-conversation system messages) to beat recency decay (§1.5). The dedicated Opus-4.8 page also covers **subagent-spawning control** ("give Claude Opus 4.8 explicit guidance around when subagents are desirable" — it spawns fewer by default) and warns that **prose style shifted** (direct/opinionated; re-evaluate voice prompts). **[VERIFIED]**

## 5. Model-specific gotchas that affect whether injected expertise is *used*

All **[VERIFIED]** unless noted.
1. **Non-generalization (the big one).** Opus 4.8 "does not silently generalize an instruction from one item to another." Broad "apply everywhere" expertise is under-applied unless scope is explicit. (*Prompting Opus 4.8*.)
2. **Literalism scales with (inverse) effort.** More literal at *low* effort; judgment-heavy application of expertise benefits from higher effort. (*Prompting Opus 4.8*.)
3. **Reasoning-trace instructions are unreliable.** Don't put "how to think" rules in the expertise expecting compliance inside the trace (§1.6).
4. **Long-context / multi-turn decay.** Expertise salient early loses influence by deep context / many turns (NoLiMa ≥50% by 32K; multi-turn −39%). Re-assert it. (§1.5.)
5. **Prompt-injection robustness *regressed* 4.7→4.8 in agentic settings.** Adversarial content in fetched pages/tool results can *out-compete* your injected expertise; enforce the non-negotiable parts with hooks (§2.1), not prose. (System Card §6.1.)
6. **Forced tool choice suppresses preamble/reasoning text.** `tool_choice:any|tool` prefills the assistant turn — no visible rationale before the tool call. Don't force when you need both. (*Tool use overview*.)
7. **Caching invalidation surprises.** `tool_choice` change, image presence change, context-editing clears, or any pre-breakpoint edit bust the cache; thinking-parameter changes invalidate message breakpoints. Keep stable expertise as an immutable high prefix. (*Prompt caching*.)
8. **No `temperature`/`top_p`/`top_k`** on Opus 4.7/4.8 (400 error) — you cannot dial determinism via sampling; steer via prompting/effort instead. (*What's new in Opus 4.8*.)
9. **"Appearance-of-success" / grader-speculation trend.** Verify outcomes with harness checks (`Stop` gates, tests) rather than trusting the model's self-report that it applied the expertise. (System Card §6.1.2.)
10. **Prefill caveat generally:** because forcing tools prefills the assistant message, and because Opus 4.x is literal, an expertise instruction like "always explain before acting" will be *silently overridden* by `tool_choice:any|tool`. Reconcile harness config with expertise intent.

## 6. Practical levers for a Claude Code agent, ranked by leverage

Ranked by how *reliably* each converts "expertise present" → "expertise applied to this decision."

1. **Hooks for anything non-negotiable (highest leverage — the only true guarantee).** `PreToolUse` deny/validate for hard rules; `Stop`/`SubagentStop` gates (incl. prompt-hooks) to enforce "apply the checklist before finishing"; `SessionStart` `additionalContext` (or CLAUDE.md) to guarantee presence; `UserPromptSubmit` to re-assert critical rules each turn. Anthropic's own framing: guarantees come from the harness, "not… relying on the LLM to choose." (§2.1)
2. **Forced tool choice + strict structured outputs for checkable expertise.** `tool_choice:tool` + `strict:true` makes schema-conforming application *mechanically guaranteed*. (§2.6)
3. **Decompose broad expertise into explicitly-scoped, positively-framed imperative rules, high in the system prompt, XML-wrapped.** This is the single biggest *prompting* lever given Opus 4.8's literal, non-generalizing interpretation. Say "apply to every X," not "apply generally." (§1.1, §3)
4. **Put always-on expertise in the always-loaded layer; use Skills only for *conditional* expertise — and invest in the `description`.** Skill bodies load only when the model matches the `description`; make it dense in both *what* and *when*. Never bury a must-always-apply rule in a conditionally-loaded body. (§2.2)
5. **Scope narrow expertise into named subagents.** Dense per-worker system prompts apply more reliably than one monolith, and keep the main context clean (better long-context behavior). (§2.4)
6. **Fight decay: re-inject the top rules mid-trajectory.** Use Opus 4.8's in-`messages` system entries (no cache bust, §2.7) and/or `UserPromptSubmit` hooks; compact and persist canonical guidelines to a **memory file** so context editing can't evict them. (§2.3, §1.5)
7. **Add 3–5 worked examples of the expertise in use.** Demonstrated application beats described application. (§3)
8. **Tune effort to the task.** Higher effort for judgment-heavy application; expect stricter literalism at low effort. Re-baseline effort levels for 4.8 (recalibrated vs 4.7). (§1.4)
9. **Verify, don't trust self-report.** Given the appearance-of-success trend, gate completion on tests/observable checks rather than the model's claim that it followed the guideline. (§5.9)
10. **Keep the expertise prefix cache-stable.** Immutable high placement → cache hits *and* maximal salience; volatile data below the breakpoint. (§2.5)
11. **Do not encode "how to think" rules expecting trace-level compliance.** Govern outputs/actions, where adherence is strong. (§1.6)
